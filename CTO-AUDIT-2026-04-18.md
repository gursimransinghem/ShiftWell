## Executive Summary

ShiftWell is in better shape than most solo-founder Expo apps I've audited. The circadian algorithm core (~3,600 lines across 13 files) is well-structured and properly tested. Supabase has RLS enabled on every table. State management is coherent (Zustand, no Redux sprawl). The founder clearly had strong AI assistance building this — the code quality is consistent and professional.

## 2. What's Working Well

**Architecture is sound.** The separation of concerns is clean:
- `src/lib/circadian/` — pure algorithm, no UI dependencies
- `src/store/` — Zustand stores with clear single-responsibility
- `src/components/` — organized by feature domain
- `app/` — Expo Router file-based routing with proper layout nesting
- `api/` — Express app factory pattern with dependency injection for testability

**Supabase integration is properly secured.** RLS is enabled on all 6 tables. Auth tokens stored in SecureStore (not AsyncStorage). Policies follow least-privilege — subscriptions table is read-only for users.

**Algorithm is well-architected.** The circadian engine follows the Two-Process Model faithfully. Code is modular: sleep-windows.ts (505 lines), energy-model.ts (430 lines), prediction-engine.ts (432 lines). Each module is independently testable.

**Feature gating is clean.** `useFeatureGate` hook + RevenueCat integration for premium features. A/B testing framework is deterministic and server-free.

**Dark-mode first.** Theme system in `src/theme/` with proper token hierarchy (colors, spacing, radius, typography).

## 3. Critical Issues

### 3.1 CRITICAL: Claude API Key Exposed in Client Bundle

**File:** `src/lib/ai/claude-client.ts`, lines 121-123

```typescript
const apiKey =
  process.env.EXPO_PUBLIC_ANTHROPIC_API_KEY ??
  process.env.EXPO_PUBLIC_CLAUDE_API_KEY;
```

The code itself has a warning comment (line 9): *"Before App Store release, route Claude API calls through a Supabase Edge Function."* But this is still using `EXPO_PUBLIC_` prefix, which means the API key gets bundled into the client JavaScript. Anyone with the IPA can extract it.

**Fix:** Create a Supabase Edge Function that proxies Claude API calls. Remove the `EXPO_PUBLIC_ANTHROPIC_API_KEY` env var entirely. This is a **must-fix before any public build** including TestFlight.

**Severity:** CRITICAL — API key theft → billing charges on your Anthropic account.

### 3.2 CRITICAL: Dashboard Inside Main App's tsconfig

The `dashboard/` directory (a Next.js project) is inside the Expo app root and gets picked up by the root `tsconfig.json`'s `include: ["**/*.ts", "**/*.tsx"]`. This causes:

```
dashboard/app/facilities/page.tsx(36,8): error TS2307: Cannot find module 'recharts'
```

**Fix:** Either:
1. Move dashboard to a separate repo (recommended — it's a different deploy target)
2. Add `"exclude": ["dashboard/**"]` to the root tsconfig.json
3. Give dashboard its own tsconfig.json with `"composite": true`

**Severity:** CRITICAL for CI — this error blocks any `tsc --noEmit` check in CI/CD.

## 4. Issues Fixed During This Audit

### 4.1 i18n Syntax Error (was blocking compilation)
**File:** `src/i18n/index.ts`, line 9
**Before:** `{ en, es as unknown as TranslationMap }`
**After:** `{ en, es: es as unknown as TranslationMap }`
Missing property key in object literal.

### 4.2 Missing expo-localization Dependency
**File:** `src/i18n/index.ts` imports `getLocales` from `expo-localization`, but it wasn't in package.json.
**Fix:** Ran `npm install expo-localization`.

### 4.3 Paywall Experiment Type Mismatch
**File:** `src/lib/growth/paywall-experiment.ts`, line 52
`getVariant()` returns `Variant` ('A'|'B'|'C') but `VARIANTS` only has 'A' and 'B'. TypeScript correctly flagged that indexing with 'C' would fail.
**Fix:** Cast return to `'A' | 'B'` since variant count is hardcoded to 2.

### 4.4 Typed Routes — Invalid Route Path
**File:** `app/index.tsx`, line 14
`router.replace('/(onboarding)')` — Expo typed routes requires a specific page, not just a group.
**Fix:** Changed to `router.replace('/(onboarding)/welcome')`.

## 5. Architecture Assessment

### 5.1 File Structure — Grade: B+

The Expo Router layout is clean. The `src/lib/` domain separation is excellent. Concerns:

- **38 planning phases in `.planning/phases/`** — these are dead weight (2.7MB). The CLAUDE.md correctly says never to auto-load these, but they still clutter the repo. Move to a separate `shiftwell-docs` repo or at minimum `.gitignore` them.
- **`dashboard/` nested inside the Expo app** — this should be a separate project. It has its own routing (Next.js `app/` directory), its own component tree, and different dependencies. Having it here creates tsconfig conflicts and confusion.
- **`docs/` is heavy** — 2.9MB of markdown across research, business, launch, marketing, vision, design, enterprise, API, and superpowers directories. This is a product/business knowledge base, not code documentation. Consider a wiki or Notion.

### 5.2 State Management — Grade: A-

15 Zustand stores is a lot, but each is focused and under 360 lines. The barrel export in `src/store/index.ts` only re-exports 5 core stores — the rest are imported directly where needed. No store-to-store circular dependencies observed.

One concern: `_layout.tsx` (root layout) does a lot of work — auth check, premium init, Google Sign-In config, calendar sync, score finalization, re-engagement scheduling. This is a common Expo pattern but it means the root layout is a 175-line god component. Consider extracting an `AppInitializer` hook.

### 5.3 API Layer — Grade: B+

The Express API in `api/` is well-structured with dependency injection for testability. Rate limiting middleware exists. JWT auth with RS256 (HS256 for tests). Routes are properly separated.

**Missing:** No CORS configuration visible. No request validation middleware (e.g., zod schemas for request bodies). No API versioning beyond the `/v1/` prefix in routes.

### 5.4 Supabase Integration — Grade: A

RLS on every table. SecureStore for auth tokens. Proper foreign key cascades. Updated_at triggers. The schema is clean and normalized appropriately for a mobile app. The only gap: no Supabase Edge Functions deployed yet (needed for the Claude API proxy mentioned above).

## 6. Missing Pieces (Pre-TestFlight)

### 6.1 No Error/Crash Reporting (HIGH)
No Sentry, Bugsnag, or Crashlytics integration. For TestFlight, you need crash reports. `expo-router` provides an `ErrorBoundary` (which is properly exported in `_layout.tsx`), but that only catches React render errors — not native crashes, unhandled promise rejections, or JS exceptions outside the render tree.

**Recommendation:** Install `@sentry/react-native` with the Expo plugin. ~30 minutes of work for critical observability.

### 6.2 No Offline Queue (MEDIUM)
The app syncs calendar data on app foreground, but there's no offline queue for failed writes. If a user is in a hospital basement (common for your target audience), changes made while offline could be lost.

**Recommendation:** Implement a simple write-ahead log in AsyncStorage. Queue operations when offline, replay when connectivity returns.

### 6.3 No Deep Linking Beyond Scheme (LOW)
`app.json` defines `scheme: "shiftwell"` but there's no universal links / associated domains configuration. This matters for email-based re-engagement links and referral flows.

### 6.4 EAS Submit Config Empty
`eas.json` has empty strings for `appleId`, `ascAppId`, and `appleTeamId`. These are needed before you can submit to TestFlight. Blocked by the LLC/Developer enrollment process (noted in CLAUDE.md).

## 7. Over-Engineering Assessment

### 7.1 Enterprise Layer — Way Too Early
`src/lib/enterprise/`, `docs/enterprise/`, `dashboard/`, `api/` — there's a full enterprise B2B layer with facility management, ROI calculators, compliance docs, and a manager dashboard. This is Phase 26-30+ content.

**For a pre-TestFlight consumer app, this is premature.** It adds complexity, testing surface, and cognitive load without generating revenue. The enterprise pivot should wait until you have 1,000+ active consumer users proving the core value proposition.

**Recommendation:** Feature-flag the entire enterprise path. Don't delete it, but don't let it block v1.0.

### 7.2 38 Planning Phases
`.planning/phases/` has 38 phase directories, from foundation (01) to advanced platform features (38). This is a 3-year roadmap baked into the repo as files. It's not harmful but it's noise.

### 7.3 AI Coaching + Predictive Scheduling + Pattern Recognition
Three separate "intelligence" systems (`src/lib/ai/`, `src/lib/predictive/`, `src/lib/patterns/`, `src/lib/intelligence/`) — these are premium features that require weeks of real user data. They're well-gated behind premium flags, so they don't block launch, but they represent significant testing liability.
